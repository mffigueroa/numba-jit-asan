# Real AddressSanitizer for Numba JIT code

An experimental, separately installable package that runs LLVM's **actual
AddressSanitizer pass** on Numba CPU JIT modules. It is not a bounds-checking
emulation and does not require a Numba or llvmlite fork. ThreadSanitizer,
MemorySanitizer, LeakSanitizer and selected UndefinedBehaviorSanitizer checks
are available as separate modes, and NumPy/Numba can be rebuilt with ASan so
their own native loads and stores are checked too. It integrates with the
[Atheris](https://github.com/google/atheris) fuzzer for coverage-guided fuzzing
of JIT code: see [Fuzzing with Atheris](#fuzzing-with-atheris).

> **AI-generated code:** This implementation, tests, and documentation were
> generated by an AI coding agent. Trust this code only as far as you trust the
> agent and your own independent review and validation. Passing tests are not a
> security audit or proof of correctness. Bugs in this experimental tool can
> miss corruption, report misleading diagnostics, or introduce memory errors.
> Obtain expert review before relying on it for security-sensitive work.

Unchecked Numba array accesses can read or write outside allocated memory.
Python's usual memory-safety guarantees do not apply to those native accesses.
The Numba option is spelled `boundscheck`, not `bounds_check`.

**Status:** working proof of concept, not production-ready or comprehensive
memory-safety coverage. Tested on Linux x86-64 and CPython 3.12 with two
validated Numba releases, each needing the external LLVM toolchain matching the
LLVM that its llvmlite embeds:

| Numba | llvmlite (embedded LLVM) | NumPy tested | External toolchain |
| --- | --- | --- | --- |
| 0.62.1 | 0.45.1 (20.1.8) | 2.3.5 | LLVM 20 (`clang-20`, `opt-20`, ...) |
| 0.68.0 | 0.50.0 (22.1.0) | 2.5.4 | LLVM 22 (`clang-22`, `opt-22`, ...) |

`numba-asan` selects the `-20`/`-22` tools from the installed Numba/llvmlite
pair ([toolchain.py](numba_jit_asan/toolchain.py)) and refuses any other pair,
because it uses private Numba hooks. Other versions/platforms need validation.

## Quick start

On Ubuntu 24.04 with LLVM 20 packages available (Numba 0.62.1):

```sh
sudo apt-get install llvm-20-dev clang-20 libclang-rt-20-dev python3-dev
python3 -m venv .venv
.venv/bin/python -m pip install -e . numba==0.62.1 llvmlite==0.45.1
.venv/bin/numba-asan build
.venv/bin/numba-asan run examples/safe.py
.venv/bin/numba-asan run examples/heap_overflow.py
```

For Numba 0.68.0, install the LLVM 22 equivalents (`llvm-22-dev clang-22
libclang-rt-22-dev`, from Ubuntu 26.04 or [apt.llvm.org](https://apt.llvm.org)
on 24.04) and `numba==0.68.0 llvmlite==0.50.0`.

The overflow example intentionally terminates with a nonzero exit code:

```text
ERROR: AddressSanitizer: heap-buffer-overflow
WRITE of size 8
... is located 0 bytes after 8192-byte region ...
Shadow bytes around the buggy address:
```

Other sanitizer modes (each is a separate run; see [Sanitizer modes](#sanitizer-modes)):

```sh
.venv/bin/numba-asan run --undefined app.py           # ASan + UBSan checks
.venv/bin/numba-asan run --leaks app.py               # ASan + LeakSanitizer
.venv/bin/numba-asan run --sanitizer thread app.py    # TSan (data races)
.venv/bin/numba-asan run --sanitizer memory app.py    # MSan (uninitialized reads)
```

To also check NumPy's and Numba's own native code (see
[Native loads/stores](#native-loadsstores-what-is-and-is-not-checked)),
rebuild them with ASan in a **dedicated** environment (about 6 minutes):

```sh
.venv/bin/numba-asan build-deps
```

Run your own application or test module:

```sh
.venv/bin/numba-asan run /path/to/application.py argument1
.venv/bin/numba-asan run -- -m unittest discover -s /path/to/tests
# If pytest is installed in this environment:
.venv/bin/numba-asan run -- -m pytest /path/to/tests
```

`numba-asan build` stores its artifacts inside the active virtual environment
(`<venv>/share/numba-jit-asan/`), because they must match that environment's
Numba/LLVM. `numba-asan run` then works from any directory. Set
`NUMBA_ASAN_BUILD_DIR` to use another location, or pass `--plugin`.

Enable this at **process startup**, before application code imports Numba.
Merely setting `LD_PRELOAD` to ASan does **not** instrument JIT instructions;
the regression tests demonstrate that distinction.

`numba-asan run` points the sanitizers at the matching `llvm-symbolizer-<N>`
(unless `external_symbolizer_path` is already set) and unsets `DEBUGINFOD_URLS`:
symbolizing system libraries must not fetch debug info over the network, which
can also stall reports indefinitely.

Do not use this on production workloads. Sanitizer runtimes are debugging
tools, introduce overhead, and are not designed as a security hardening layer.
Do not run intentionally corrupting examples without the sanitizer launcher.

## Fuzzing with Atheris

[Atheris](https://github.com/google/atheris) is a coverage-guided Python fuzzer
built on libFuzzer. `numba-asan run --fuzz` makes it effective on Numba code:

```sh
.venv/bin/python -m pip install -e ".[fuzz]"   # installs Atheris (2.3.0 on Python 3.10)
.venv/bin/numba-asan build          # also builds the Atheris runtime
.venv/bin/numba-asan run --fuzz fuzz_parser.py -max_total_time=600 -rss_limit_mb=2048
```

```python
# fuzz_parser.py: an ordinary Atheris harness, nothing numba-asan specific
import sys
import atheris
import numpy as np
from numba import njit

@njit(boundscheck=False)
def parse(data):
    if data.size >= 6 and data[0] == 0x4E and data[1] == 0x42 and data[2] == 0x41 and data[3] == 0x21:
        table = np.zeros(4, dtype=np.uint8)
        table[data[4]] = data[5]  # unchecked index from the input
    return 0

def TestOneInput(raw):
    parse(np.frombuffer(raw, dtype=np.uint8))

atheris.Setup(sys.argv, TestOneInput)
atheris.Fuzz()
```

This finds the overflow behind the 4-byte magic within seconds, writes a
`crash-*` input, and reports it at the Python source line:

```text
==23287==ERROR: AddressSanitizer: heap-buffer-overflow on address 0x7a77b05e0084 ...
WRITE of size 1 at 0x7a77b05e0084 thread T0
    #0 0x7e27b14f94ea in __main__::parse(Array<unsigned char, 1, C, readonly, aligned>) /tmp/fz/fuzz_parser.py:11:1 (numba-jit+0x4ea)
SUMMARY: AddressSanitizer: heap-buffer-overflow /tmp/fz/fuzz_parser.py:11:1 in __main__::parse(...)
```

What `--fuzz` does, following Atheris's
[native extension fuzzing](https://github.com/google/atheris/blob/master/native_extension_fuzzing.md)
guide:

- **JIT coverage.** JIT code gets the equivalent of Clang's
  `-fsanitize=fuzzer-no-link` (edge counters, PC tables, comparison and
  indirect-call tracing) on top of ASan. Without it, libFuzzer cannot see
  branches inside `@njit` functions; the magic above would take ~2³² guesses.
- **Matching runtime.** `numba-asan build` links the matching LLVM's ASan runtime with
  libFuzzer into `asan_with_fuzzer.so` (as Atheris's
  `merge_libfuzzer_sanitizer.sh` does), and `--fuzz` preloads it. Do **not**
  preload Atheris's own `asan_with_fuzzer.so`: it is from an older LLVM, does
  not match the JIT instrumentation, and on current kernels it can loop
  endlessly printing `AddressSanitizer:DEADLYSIGNAL`. The launcher refuses it
  before running any tool. LLVM tools (`opt`, `llvm-nm`, `llvm-symbolizer`,
  `clang`) are always run without `LD_PRELOAD`, with a timeout: an orphaned
  `opt --version` that inherited such a runtime once wrote ~100 GB of
  `DEADLYSIGNAL` lines to a log.
- **Bytecode instrumentation.** `atheris.instrument_imports()` and
  `atheris.instrument_all()` rewrite Python bytecode, which Numba cannot
  compile. numba-asan records the original bytecode for everything Atheris
  instruments and compiles `@njit` functions from it; Python code keeps
  Atheris's coverage, JIT code gets native coverage.
- **Child processes.** libFuzzer's `-fork`, `-jobs`/`-workers` and `-merge`
  modes re-run the harness; numba-asan makes those children start under the
  launcher too, so their JIT code is instrumented.

Usage notes:

- Use `--fuzz` both to fuzz and to reproduce: `numba-asan run --fuzz harness.py crash-<hash>`.
- Pass `-use_value_profile=1` for magic values and other comparison-guarded
  JIT branches. Without it, discovery depends on the seed, and it gets less
  likely when instrumented NumPy/Numba share the coverage map. In one test,
  seed 1 missed a 4-byte magic in 2M runs without it, and found it in
  221k runs with it.
- `--fuzz --undefined` adds the UBSan checks.
- With `-fork`, call your target once before `atheris.Fuzz()` (for example
  `TestOneInput(b"")`): the fork-mode parent only tracks coverage of JIT code
  it has compiled. numba-asan warns otherwise. `-jobs`/`-workers` do not need this.
- `numba-asan build-deps --fuzzer` also adds native coverage to NumPy and Numba.
- Leak detection is off (Atheris recommends `-detect_leaks=0` for Python);
  `--fuzz` cannot be combined with `--leaks`.
- Timeouts (`-timeout=N`), `-rss_limit_mb` and `-malloc_limit_mb` work as in
  libFuzzer; timeout stacks point at the hanging JIT line.

**Bound your fuzzing runs.** A sanitizer process holds ~0.8-1 GiB at baseline,
each `-fork`/`-jobs` worker is a separate process, and a misbehaving runtime can
produce output endlessly. Always pass `-rss_limit_mb` and a time limit
(`-max_total_time`), and on shared machines run inside a cgroup with hard
memory, swap and task limits, and redirect output to a file. For example:

```sh
systemd-run --user --scope -p MemoryMax=4G -p MemorySwapMax=0 -p TasksMax=64 \
    .venv/bin/numba-asan run --fuzz fuzz_parser.py -max_total_time=600 \
    -rss_limit_mb=2048 > fuzz.log 2>&1
```

Or run in a container with `--memory`/`--pids-limit`.

### Writing effective fuzz targets for Numba code

These lessons come from fuzzing about 100 open-source Numba packages (Numba 0.68 /
LLVM 22). Each fixes a way a target failed to find bugs or reported false
ones. They apply whether a target is handwritten or generated.

| Do | Why (what went wrong otherwise) |
| --- | --- |
| **Warm up before `atheris.Fuzz()`.** Call the public API once per type signature the target can produce: each dtype, ndim, contiguous vs. sliced (`A` layout), read-only vs. writable, `None` vs. value for optional arguments. | Disk caches are off under the sanitizer, and compiling instrumented JIT code takes seconds to minutes per package. Compilation inside an input exceeded `-timeout`, which libFuzzer reports as a false *timeout*. Inputs of 55-89 s were observed. |
| **Generate few signatures.** Pick dtypes/layouts from a small fixed list matching the warm-up. | Every new signature is a compilation in the middle of fuzzing: slow inputs, low throughput, false timeouts. |
| **Allow for import-time compilation.** Give startup (import + warm-up) its own budget, outside `-max_total_time`. | Packages compiling eager signatures at import took up to 13 min and 2.1 GiB to import under ASan. |
| **Instrument only the product:** `with atheris.instrument_imports(include=["pkg"])`. Import NumPy/SciPy and other dependencies first, outside the block. | Without `include`, importing one package (via scikit-learn and SciPy) spent more than 3 minutes on bytecode instrumentation before the first input. |
| **Name targets `fuzz_<pkg>.py`, never `<pkg>.py`.** | The script directory is on `sys.path`, so a target named like the package shadows it (circular-import failure). |
| **Let sizes cross the kernels' fixed capacities cheaply.** Derive shapes from fuzzer integers and fill them with patterns, repeated blocks or tiling of real data. | A target spending one input bit per array element capped its inputs far below a kernel's fixed-size internal buffer, so overflows of that buffer could never be reached. |
| **Pass `-len_control=0`** for targets that read choices from the input (`FuzzedDataProvider`). | libFuzzer grows inputs slowly: after 28k runs the length limit was still 21 bytes, so choices read late in an input were never exercised. |
| **Pass `-use_value_profile=1`.** | A 4-byte magic compared in JIT code was missed in 2M runs for one seed without it, and found in 26k-221k runs with it. |
| **Set `-rss_limit_mb` from the measured baseline**, at least 1-2 GiB above it (4096 is a safe default). Set `ASAN_OPTIONS=allocator_may_return_null=1:max_allocation_size_mb=<half the RSS limit>`. | Sanitized processes start at 0.8-1.9 GiB with scientific dependencies loaded. With 2048, several packages reported false *OOM* findings. Mutated sizes also request single 10-12 GB allocations. libFuzzer's malloc limit reports these as OOM and stops fuzzing. With both options, ASan refuses them first, and NumPy and Numba raise `MemoryError`, which the target handles. |
| **Cap Numba's threads** (`NUMBA_NUM_THREADS=2`) for `parallel=True` kernels. | With the default thread count on a busy host, each fork/join of a `prange` loop made inputs take seconds, up to about 170 s. |
| **Keep inputs fast: at least ~5 executions/s after warm-up.** Shrink per-input work: iterations, bootstrap counts, model sizes. | Runs of 24-217 executions per minute (resampling- and model-fitting APIs) explore almost nothing, but still look "clean". |
| **Treat only deliberate rejections as handled:** an explicit `raise` in the product, or validation inside a dependency. Never catch `Exception` or Numba's `TypingError`; generate valid types instead. | A deliberate `ValueError` from a package's own validation was misreported as a crash. Broad catches would hide `IndexError`/`ZeroDivisionError` raised from JIT code, which are real robustness findings. |
| **Do not stop at the first robustness finding.** Record implicit exceptions and keep fuzzing; let only sanitizer reports abort. | libFuzzer stops at the first crash, and shallow exceptions (empty inputs, zero sizes) would hide deeper memory errors. libFuzzer's `-fork` mode, which could continue past crashes, does not work under `numba-asan run --fuzz` yet. |
| **Fuzz unvalidated parameter values too** (negative sizes, empty arrays, the endpoints of documented ranges). | Unchecked indexing in JIT code is commonly reached through parameters a package never validates, and through boundary values its documentation allows. Fuzzing only typical values misses both. |
| **With `numba-asan build-deps`, prefer the ASan-only build** unless the dependencies themselves are under test. | Coverage-instrumented NumPy/Numba add ~330k counters that dilute guidance away from the JIT code (221k vs. 26k runs for the same bug). |

A minimal skeleton:

```python
import sys
import atheris
import numpy as np                      # dependencies: not instrumented

with atheris.instrument_imports(include=["mypkg"]):
    import mypkg

DTYPES = (np.float64, np.int64)          # few signatures

def warm_up():
    for dtype in DTYPES:                  # every signature the target generates
        mypkg.public_function(np.arange(8, dtype=dtype), 3)

def TestOneInput(data):
    fdp = atheris.FuzzedDataProvider(data)
    n = fdp.ConsumeIntInRange(0, 1 << 18)            # can cross fixed capacities
    block = np.asarray(fdp.ConsumeFloatList(16) or [0.0])
    values = np.resize(block, n).astype(fdp.PickValueInList(DTYPES))
    window = fdp.ConsumeIntInRange(-8, 300)          # includes unvalidated values
    try:
        result = mypkg.public_function(values, window)
    except ValueError:                    # only if mypkg raises it deliberately
        return
    assert result.shape == values.shape   # documented invariants only

if __name__ == "__main__":
    warm_up()
    atheris.Setup(sys.argv, TestOneInput)
    atheris.Fuzz()
```

```sh
NUMBA_NUM_THREADS=2 ASAN_OPTIONS=allocator_may_return_null=1:max_allocation_size_mb=2048 \
  .venv/bin/numba-asan run --fuzz fuzz_mypkg.py corpus/ -max_total_time=600 \
  -rss_limit_mb=4096 -timeout=60 -use_value_profile=1 -len_control=0
```

To avoid writing targets at all, generate them from existing tests. The
integration corpus's `numba_autofuzz` records the public-API calls its tests
make, then replays and mutates them with these defaults built in.

## What is implemented

1. The launcher re-executes Python with the matching Clang ASan shared runtime
   preloaded and `PYTHONMALLOC=malloc` to avoid CPython small-object arenas.
2. A small LLVM pass plugin sets the function-level `sanitize_address`
   attribute and runs LLVM's `AddressSanitizerPass`, including stack/global
   instrumentation, after Numba's normal optimization/linking pipeline.
3. The instrumented module is parsed back into llvmlite and compiled by MCJIT.
   There is no unsafe sharing of C++ LLVM pointers across LLVM installations.
4. Module constructors register ASan globals explicitly. ELF section-based
   global registration is disabled because MCJIT does not provide the linker
   start/stop symbols. Unique exported constructor/destructor names prevent
   collisions between JIT modules.
5. Globals remain registered until their execution engine dies. This matters
   for ufunc wrapper libraries that Numba drops while retaining native code.
6. Pristine optimized IR is used when linking JIT libraries, so instrumentation
   is applied once to the final linked module, rather than repeatedly.
7. All Numba disk caches are disabled for this process. Existing unsanitized
   objects cannot bypass instrumentation, and instrumented objects cannot
   contaminate normal caches.
8. An ASan-built native bridge replaces the fixed-size NRT JIT allocation
   entry points. Payloads are allocated separately from `MemInfo`, with exact
   malloc/ASan boundaries instead of accessible alignment padding. The bridge
   preserves original metadata reference counting, custom destructor calls,
   safe allocation fill patterns, and payload alignment.
9. NRT external-allocator payloads get manually poisoned prefix/suffix guards.
   The original custom allocator receives its own base pointer back at free;
   its storage is unpoisoned before free-list metadata writes. The bridged NRT
   API table also supplies sanitizer-aware allocation functions.
10. A NumPy NEP 49 policy uses direct malloc/calloc/realloc/free instead of the
    small-buffer cache. Ordinary `threading.Thread` targets install this policy
    too; NumPy policies are thread/context-local.
11. Debug info is enabled **after** resolving normal bounds-check defaults.
    Captured JIT object code and address ranges let the launcher rewrite
    `<unknown module>` JIT frames in every sanitizer report (see below).
12. The same plugin provides TSan, MSan and UBSan pipelines; the launcher picks
    the matching runtime. See [Sanitizer modes](#sanitizer-modes).

The plugin uses LLVM's attribute API. In this pinned llvmlite version,
`ValueRef.add_function_attribute("sanitize_address")` attaches it at the return
attribute position and produces invalid IR, so that API is not suitable here.

## Verified coverage

Run the integration tests:

```sh
.venv/bin/python -m unittest discover -s tests -v
.venv/bin/python -m pip check
```

Buggy programs execute only in isolated subprocesses. The tests assert real
ASan error classes, access widths, shadow-byte reports, and nonzero exit
statuses, not merely the presence of runtime symbols.

Covered examples include:

- Heap out-of-bounds reads, writes, and excessively negative indices with
  `boundscheck=False`.
- Use-after-free through an externally allocated array buffer.
- Exact NRT one-past-end/underflow checks, including a negative offset that
  previously could reach metadata/padding.
- Custom NRT allocators backed by malloc or anonymous mmap, with guard checks,
  metadata canary preservation, alignment and correct base-pointer freeing.
- Small NumPy buffer use-after-free, per-thread policies and explicit fresh
  context installation.
- Embedded JIT constant globals and stack allocations (the latter via a test
  intrinsic that preserves an addressable stack array).
- Linked `@njit` functions, `@cfunc`, `@vectorize`, and `@guvectorize`.
- `parallel=True` / `prange` on Numba's workqueue backend, including vectorized
  stores. This verifies ASan, not race detection; TBB/OpenMP are not tested.
- Safe execution, IR instrumentation, cache isolation, script/module execution,
  and the installed CLI outside the source directory.
- JIT frames rewritten in place with the Numba function and exact Python
  source line, including the `SUMMARY:` line.
- UBSan: out-of-range shifts (too large and negative) and float-to-int
  overflows (including NaN), opt-in behavior, in-range edge cases, and
  combination with TSan.
- TSan: races between `nogil` threads and between `prange` iterations writing
  a shared element; lock-protected code and recognized reductions are clean.
- MSan: branching on and returning values read from uninitialized `np.empty`
  memory; data written by NumPy/CPython is not falsely reported.
- LSan: an NRT allocation leaked by JIT code (allocation stack points to the
  JIT source line), the scoped `check()` API, and no reports for live Python
  objects referenced only from running frames.
- Atheris (`tests/test_atheris.py`): finding a JIT bug behind a 4-byte magic
  and reproducing it from the crash file; `instrument_imports()` and
  `instrument_all()` with `@njit` code; `-fork` children sanitized with corpus
  accumulation, and the warning when it cannot accumulate; timeouts pointing
  at the hanging JIT line; UBSan under fuzzing; refusing Atheris's prebuilt
  runtime. Every fuzzer run is bounded in time, memory and captured output.
- Native dependencies: a use-after-free read inside NumPy's C reduction loop
  and inside Numba's C runtime. Stock wheels silently return wrong data; with
  `build-deps`, both become ASan reports in the native source. CI runs the full
  suite in both configurations and asserts which one it is testing.
- The same native C++ store compiled with and without ASan: only the instrumented
  library detects the overflow, with its native file and line in the report.

## JIT crash diagnostics

MCJIT memory is not a loaded ELF image, so sanitizers print JIT frames as
`<unknown module>`. The launcher captures each report through the sanitizer's
`log_path` option and rewrites those frames in place using the JIT object code
and address ranges recorded at compile time:

```text
WRITE of size 8 at 0x73efb12a0900 thread T0
    #0 0x759fb150105f in __main__::write(Array<long long, 1, C, mutable, aligned>, long long) /path/examples/heap_overflow.py:8:1 (numba-jit+0x5f)
    #1 0x759fb1501271 in cpython::__main__::write(...) ?? (numba-jit+0x270)
    #2 0x759fb15063a0 in compile_and_invoke(...) /io/numba/_dispatcher.cpp:1152:28
SUMMARY: AddressSanitizer: heap-buffer-overflow /path/examples/heap_overflow.py:8:1 in __main__::write(...)
```

This works for ASan, LSan, UBSan, TSan and MSan reports. Generated wrappers
(`cpython::...`) have no Python line, and `prange` kernels are generated from
the loop body, so their file appears as `<string>` with the original line
number. Optimized/inlined code can produce surprising locations.

Reports are printed by the launcher after the program exits. If you set your
own `log_path` in `ASAN_OPTIONS`/`TSAN_OPTIONS`/`MSAN_OPTIONS`/`UBSAN_OPTIONS`/
`LSAN_OPTIONS`, reports go there unmodified. Use `NUMBA_ASAN_JIT_DIR` to retain
JIT objects (one `run-*` subdirectory per launch); they contain your compiled
code and source paths, so treat them as sensitive. Otherwise they are deleted.

## Native loads/stores: what is and is not checked

A load/store is a machine instruction reading/writing memory. ASan's allocator
creates poisoned redzones, but **only instrumented instructions check those
redzones**. Preloading ASan cannot retrofit checks into an existing Python,
NumPy, BLAS, or other extension binary. This package builds its own native
bridge with ASan, and can rebuild NumPy and Numba:

```sh
.venv/bin/numba-asan build-deps   # reinstalls the installed numpy/numba versions from source
```

To reuse the builds across environments (for example one disposable venv per
CI job), cache the instrumented wheels:

```sh
.venv/bin/numba-asan build-deps --wheelhouse ~/numba-asan-wheels   # ~3 min once, then seconds
```

Wheels are cached per LLVM major and sanitizer flavor (`llvm22-address/`,
`llvm22-address-fuzzer-no-link/`), and matched by package version and Python
tag. The instrumentation check runs after every install, cached or not.
In environments created by uv, which have no pip, pip is installed to build
the wheels.

This compiles every NumPy and Numba extension module with the matching Clang and
`-fsanitize=address` (verified afterwards by checking each `.so` for ASan
symbols). Consequences:

- Use a dedicated virtual environment. Rebuilt modules require the ASan runtime,
  so they only import under `numba-asan run`.
- NumPy is built **without BLAS/LAPACK** (its own instrumented fallback loops are
  used instead), so linear algebra is slower and BLAS itself is not checked.
- Numba's OpenMP and TBB threading layers are not built; `workqueue` is used.
- CPython itself, SciPy, BLAS and any other extension remain uninstrumented
  unless you rebuild them the same way.

For another C/C++ shared library, the essential build pattern is:

```sh
clang++-22 -shared -fPIC -g -O1 -fsanitize=address \
    -fno-omit-frame-pointer your_library.cpp -o your_library.so
```

Use that library under the launcher so it resolves the same preloaded runtime.
Do not load multiple independent ASan runtimes. For Python extensions, pass
equivalent compiler/linker flags through their supported build system, install
them in an isolated environment, and verify detection with a deliberate native
failure. Interpreter and dependency builds need their own build-system-specific
instructions; a wheel from PyPI is not presumed instrumented.

ASan interposes malloc/free, so this testing environment uses ASan's allocator,
not a proof that corruption of the production libc allocator's metadata is
impossible. Separating payload and NRT metadata and guarding custom allocations
removes the demonstrated adjacent-metadata exposure; arbitrary indices that
land in another live allocation remain a limitation.

## Important blind spots

**Real ASan is not the same as checking every array's logical bounds.**

- A slice/view can overflow its logical shape while staying within the backing
  allocation. ASan normally cannot detect this, just as it cannot detect every
  C++ subobject/container overflow without extra annotations.
- The fixed-size NRT allocation hooks are covered, but the original Python
  `rtsys.meminfo_alloc` entry point and native extensions that obtained the
  original NRT API directly bypass the replaced JIT helper table. Resizable
  NRT allocations retain their original implementation and have not received
  the same lifecycle/allocator regression coverage. Third-party runtime APIs
  are not automatically intercepted.
- The bridge uses private Numba `MemInfo` layout and version-pinned hooks.
  Custom allocator identity is stored in bridge state, not `MemInfo.external`,
  because metadata itself must be freed by the original NRT allocator.
  Code inspecting the experimental external-allocator identity may therefore
  behave differently.
- Custom allocator guards detect payload over/underflows, not accesses within
  the allocator's own uninstrumented implementation. Guards are unpoisoned
  before calling custom free to allow legitimate free-list writes. A pool
  retaining that block needs its own free/reuse poisoning for use-after-free
  coverage. Arbitrary custom allocators outside these NRT entry points need
  explicit integration.
- NumPy arrays allocated before policy installation or after another policy
  replaces ours retain their original allocator. Fresh explicit contexts,
  `Thread` subclasses overriding `run`, and native-created Python threads
  must install the policy themselves:

  ```python
  from numba_jit_asan.allocators import install_numpy_policy
  install_numpy_policy()  # inside that thread/context, before creating arrays
  ```

  Custom NumPy policies are intentionally not blindly poisoned: their own
  metadata, sharing and ownership rules require a policy-specific adapter.
- Without `build-deps`, NumPy's and Numba's native code is uninstrumented.
  CPython, BLAS and other extensions remain uninstrumented in every mode.
  Allocator interception still works for ordinary malloc/free, and
  instrumented JIT code accessing those allocations **is** checked.
- JIT frame rewriting depends on the launcher capturing reports; generated
  functions without debug info remain line-less.
- Only CPU JIT code is hooked. CUDA, AOT, child-process startup strategies,
  and arbitrary third-party codegen subclasses are not covered.
- Like normal ASan, checks apply to surviving optimized accesses, require
  exercised execution paths, and do not guarantee detection of every invalid
  pointer (for example, one landing in another live allocation).

Keep a separate bounds-checking CI job where practical:

```sh
NUMBA_BOUNDSCHECK=1 .venv/bin/python -m unittest discover -s /path/to/tests
```

It complements ASan by checking logical array indices. It does not replace
ASan for pointer lifetime errors or unchecked native intrinsics.

## Sanitizer modes

Each mode is a separate process; ASan, TSan and MSan cannot be combined.

| Mode | Flag | What it catches in JIT code | Runtime |
| --- | --- | --- | --- |
| ASan | (default) | Heap/stack/global out-of-bounds, use-after-free | Preloaded `libclang_rt.asan` |
| UBSan | `--undefined` | Out-of-range shifts, float-to-int overflow (incl. NaN) | Handlers in the ASan/TSan runtime |
| LSan | `--leaks` | Leaked NRT allocations (e.g. reference-count bugs) | ASan runtime |
| TSan | `--sanitizer thread` | Data races between threads and `prange` iterations | Preloaded `libclang_rt.tsan` |
| MSan | `--sanitizer memory` | Branching on / returning uninitialized `np.empty` data | Custom CPython launcher |

### UndefinedBehaviorSanitizer (`--undefined`)

Numba lowers `x << n` and float-to-int conversions to LLVM `shl`/`fptosi`, which
produce *poison* (undefined results) for shift amounts outside `[0, width)` or
values not representable in the target type. In practice `1 << 70` returned
`64` and `np.int32(1e300)` an arbitrary value. A plugin pass inserts checks
**before optimization** (so LLVM cannot exploit the poison first) and calls the
real UBSan runtime handlers:

```text
ub.py:6:1: runtime error: shift exponent 70 is too large for 64-bit type 'int64'
```

Only these two checks exist. Integer division and modulo are not instrumented
because Numba already guards zero divisors and `INT_MIN // -1` explicitly.
Most Clang UBSan checks (signed overflow, alignment, ...) depend on C/C++
language rules that do not match NumPy's wrapping arithmetic. Type names are
derived from LLVM IR (`'int64'`), which does not record signedness; shift
amounts are reported as signed. By default the run halts on the first error
(`UBSAN_OPTIONS=halt_on_error=0` to continue).

### LeakSanitizer (`--leaks`)

LSan normally checks at process exit, where it reports CPython's
intentionally retained memory. `--leaks` disables that and instead checks
after your script finishes but **before** interpreter shutdown, when live
Python objects are still reachable; exit status 23 indicates leaks. CPython
3.11+ keeps active frames in mmap-backed stacks LSan does not scan, so frame
stack mappings are temporarily registered as roots during each check. Check
at specific points (for example, around each test):

```python
from numba_jit_asan.leaks import check
check()  # raises numba_jit_asan.leaks.LeakError if anything is unreachable
```

Known compiler-internal leaks in `libllvmlite.so` and CPython frame objects
created for stack introspection are suppressed
([lsan.supp](numba_jit_asan/lsan.supp)). Leaks are reported only for
allocations that are unreachable; a leaked object still referenced from a
live global or cache is not detected, and conservative scanning can treat
integers that look like pointers as references.

### ThreadSanitizer (`--sanitizer thread`)

JIT functions get LLVM's TSan instrumentation; Python threads, the GIL and
Numba's `workqueue` pool use pthreads that TSan intercepts, so their
synchronization is understood. Races are reported with both JIT stacks and
the run exits with 66. Caveats:

- TSan reports races it observes: accesses must actually be unordered in the
  executed interleaving. Very short `nogil` calls may be ordered by the GIL
  hand-off and go unreported.
- TSan must also restore the stack of the *earlier* racing access from a
  bounded per-thread trace. If the other thread made more than roughly
  200,000 instrumented accesses since then, the race is dropped silently.
  `numba-asan run` sets `TSAN_OPTIONS=history_size=7` (the maximum; about
  100,000 with the default). A typical case is a shared accumulator that LLVM
  loads before and stores after a long `prange` chunk. Reproduce races with
  small inputs: a race needs overlapping threads, not large data. In one
  test, 200,000 elements were detected every time, while 5,000,000 lost the
  update every time and were never reported.
- CPython, NumPy and Numba's C code are uninstrumented: races *inside* them
  are not detected, and synchronization implemented with uninstrumented
  atomics would be invisible (none is used on the tested paths).
- Only the `workqueue` threading layer is tested. OpenMP/TBB need TSan-built
  runtimes.
- Kernels with high ASLR entropy may need `sysctl vm.mmap_rnd_bits=28`.

### MemorySanitizer (`--sanitizer memory`)

MSan has no shared runtime that could be preloaded, so `numba-asan build`
creates `numba-msan-python`, a CPython entry point (embedding the system
`libpython`) linked with the MSan runtime. Because CPython and NumPy are not
MSan-instrumented, their writes do not update MSan's shadow memory. To avoid
false positives:

- `poison_in_malloc=0`: heap memory is treated as initialized, except NRT
  payloads allocated by JIT code (`np.empty`), which the bridge marks
  uninitialized.
- Stack objects whose address is passed to an uninstrumented function are
  treated as initialized after the call (out-parameters).
- Arguments passed from JIT code to uninstrumented functions are checked
  (`noundef`), so uninitialized values escaping to Python are reported.

Limitations: NumPy arrays created by Python (`np.empty` outside JIT code) are
not tracked; reports do not include an allocation origin (MSan can only record
one through a process-wide flag that would race with other threads); MCJIT
cannot resolve MSan's initial-exec thread-locals, so JIT code obtains them
through small getter functions. Requires a shared `libpython`
(`python3-dev` on Ubuntu). This mode is the most experimental.

## Path to an upstream/community feature

This repository demonstrates that a separate extension package is viable.
No forks are necessary to reproduce the demonstrated ASan detections.
For maintainable upstream support, the responsibilities divide naturally:

**llvmlite**

- Expose LLVM's sanitizer passes and proper function attribute insertion.
- Manage pass settings/version compatibility without an external `opt` process.
- Provide JIT constructor/destructor and debug-object registration hooks.

**Numba**

- Provide a supported sanitizer compilation option/hook at the final
  optimization/codegen boundary, with propagation to nested functions,
  ufuncs and parallel-generated kernels.
- Include sanitizer configuration/runtime ABI in cache keys instead of
  disabling caches. Never reuse unsanitized objects for a sanitized run.
- Make NRT allocations sanitizer-aware: separate metadata from payload or
  poison allocator-owned padding/redzones, preserving alignment and correctly
  unpoisoning before destructor/debug-fill/realloc/free operations. Never
  poison live metadata or blindly poison shared array-view storage.
- Preserve source debug information and register JIT code with a sanitizer
  symbolization mechanism.
- For UBSan, add semantic checks during lowering rather than relying on Clang
  to recover Python/NumPy semantics from already-generated LLVM IR.

**NumPy and the native dependency stack**

- Use a debug memory policy (NEP 49) with ASan-compatible allocation/free
  behavior, or sanitizer-aware caching, to expose small-buffer lifetimes.
- Rebuild native components with the appropriate sanitizer for end-to-end
  coverage; TSan and especially MSan require their own validated stacks.

These allocator, diagnostic and sanitizer-mode bridges demonstrate a direction
for upstream support, but do not justify advertising "full sanitizers." The
remaining priorities are resizable/native NRT entry points, arbitrary custom
allocator lifecycle adapters, sanitizer builds of CPython/BLAS and the threading
runtimes, MSan allocation origins, and native JIT registration with sanitizer
symbolizers (MCJIT TLS relocation support would remove the MSan getters).

## CI and distribution

[GitHub Actions](.github/workflows/ci.yml) runs on pushes, pull requests and
manual dispatch, once per validated Numba release. Ubuntu 24.04 installs the
matching LLVM (20 from Ubuntu, 22 from apt.llvm.org) and Python development headers,
installs Atheris, builds the plugin, bridges, Atheris runtime and MSan
launcher, and runs the full regression suite (ASan, UBSan, LSan, TSan, MSan,
Atheris) twice: with stock NumPy/Numba wheels and after
`numba-asan build-deps --fuzzer`. The second job asserts that the dependencies
really carry ASan and fuzzer coverage. The stock Numba 0.68.0 job builds and uploads the Python wheel.
Intentionally failing sanitizer cases are subprocess tests whose expected
failures are asserted by the test runner.

This is CI plus a downloadable build artifact, **not automatic PyPI publishing**.
The wheel includes native source, not portable prebuilt LLVM plugins; users
still run `numba-asan build` with matching toolchains. Publication credentials,
release policy and packaging review should be configured separately.
